# DiagnosticIQ: AI Diagnostic Copilot for Heavy-Duty Truck Technicians

A technician enters **symptoms, J1939 fault codes, or both**, with the vehicle optional. The system gets evidence from two sources and has Groq turn it into a ranked diagnosis. Each claim is tagged with its source.

```
frontend (React/Vite :5173)
   │  POST /diagnose {symptoms, fault_codes, vehicle}       GET /decode?code=...
   ▼
backend/app.py (FastAPI :8008)
   ├─► sql_pipeline   exact J1939 lookup in Neon Postgres
   │                  → SAE meaning, severity, manufacturer record (or an explicit "none")
   ├─► rag_pipeline   semantic search over service-doc chunks in Chroma
   │                  → matched faults, symptoms, step-by-step procedures
   └─► backend/synthesis.py   one Groq call merges both
                      → causes + steps tagged [Code DB] / [Service docs] / [General knowledge]
```

## Folder layout

| Folder | What it does |
|---|---|
| `frontend/` | React UI: New Diagnosis form, Results page, History and Dashboard |
| `backend/` | The merged API. `app.py` holds the endpoints, `hybrid.py` runs both branches, `synthesis.py` makes the final Groq call, and `bootstrap.py` sets up paths and env |
| `sql_pipeline/` | J1939 database: schema, loader, `fetch_fault_code`, text extractor and `resolve()`. See its README |
| `rag_pipeline/` | Vector DB: ingest, chunk, Groq severity tagging, embed into Chroma. `api.py` still works standalone |
| `tests/` | End-to-end API tests for the merged system (`sql_pipeline/tests` covers the SQL branch alone) |

## One-time setup

```powershell
cd D:\Synapse1.0
pip install -r requirements.txt
copy .env.example .env                # then fill in DATABASE_URL and GROQ_API_KEY
                                      # (sql_pipeline\.env is also read if you keep it there)

python sql_pipeline\load_data.py      # load the J1939 CSVs into Neon (~1 min; safe to re-run)

# Download the Zenodo dataset (CC-BY-4.0, https://zenodo.org/records/15626055) to
#   rag_pipeline\vector_database_extracted\automotive_faults_aktc_obike_et_al.json
cd rag_pipeline; python pipeline.py; cd ..   # build the Chroma store (Groq tags are cached)

cd frontend; npm install; cd ..
```

## Run

Use two terminals:

```powershell
python backend\app.py                 # API on http://localhost:8008  (Swagger UI: /docs)
cd frontend; npm run dev              # UI on http://localhost:5173
```

## Test

```powershell
python -m pytest -v                   # everything: SQL-branch tests + merged API tests

```

## API

| Method | Path | Body / params | Returns |
|---|---|---|---|
| GET | `/health` | none | DB row count and vector chunk count |
| GET | `/decode` | `?code=SPN 102 FMI 2` | `{component, description, severity, manufacturer_specific_data}`. Returns 404 for unknown or OBD-II codes |
| POST | `/diagnose` | `{symptoms, fault_codes: [], vehicle: {make, model, year, engine}}` | `{query, retrieval_query, matches[], answer, sql, obd_codes, warnings}` |
| POST | `/query` | `{query}` | The same response, symptom-only. Kept for compatibility with `rag_pipeline/api.py` |

`sql` is the output of `sql_pipeline`'s `resolve()`; its contract is documented in `sql_pipeline/README.md`. `matches` has the same fields as the original RAG API, plus `distance`. The response also includes `relationship` (`{code: A|B|C|D, label}`) and `cited_service_docs`.

### How the answer is built (`backend/synthesis.py`)

The answer has 7 sections:

1. **Fault Code Analysis.** Generated by code from the J1939 database, with no LLM involved. It includes the exact line "Generic J1939 decode only — no manufacturer-specific record was found." when that applies.
2. **Symptom Analysis** (LLM, sections 2–6).
3. **Combined Analysis**, which contains exactly one relationship class:
   - A. DIRECTLY CONSISTENT
   - B. POTENTIALLY RELATED
   - C. NOT DIRECTLY RELATED
   - D. INSUFFICIENT INFORMATION
4. **Supported/Potential Causes.** Unranked, and each item is labelled as a retrieved fact, a manufacturer record, service-doc similarity, or an inference.
5. **Recommended Diagnostic Checks.**
6. **Safety.**
7. **Source / Evidence.** Generated by code, listing only what the answer actually used.

Checks applied after the LLM writes sections 2–6 (each correction is added to `warnings`):
- A source label naming something that wasn't retrieved (e.g. `[Code DB]`) is replaced with `[Inference]`.
- An SPN number that isn't a supplied code or on the verified reference list is removed. Names of allowed SPNs are rewritten from the database.
- A numeric value with a unit that doesn't appear in the evidence (e.g. "typically 5 V") is marked `[unverified value]`.
- A missing or ambiguous relationship class is reported.

The service-doc search uses the symptom text only, so the symptom is analysed separately from the code.

## Known limits

- **The service-doc dataset is small and generic.** It has 99 records about general automotive faults and nothing truck-specific. The synthesis prompt tells the model to ignore matches that don't fit.
- **Manufacturer-specific J1939 data exists only for SITRAK.** For other brands the answer relies on SAE-standard decodes and says so.
- **OBD-II codes (P0299 etc.) are not in the J1939 database.** They are passed to the LLM and interpreted from general knowledge.
- **Groq's free tier has limits per model:** 200k tokens/day and 8k tokens/minute. One diagnosis uses about 2.5–3.5k tokens, so that's roughly 60 diagnoses per day per model, and only 2–3 per minute.
  - When the main model (`GROQ_MODEL`) is over its limit, the answer comes from the next one in `GROQ_FALLBACK_MODELS` (default `qwen/qwen3.8-27b`).
  - A daily limit is never waited out; the request moves on immediately.
  - If every model is limited, `/diagnose` returns the database facts (sections 1 and 7) within seconds, and "Data notes" explains why.
